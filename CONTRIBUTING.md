# Contributing

Thanks for helping. Two rules hold for every change:

- No score is ever typed by hand. Results come only from real runs, and the
  report is generated by `bench report`.
- Nothing is changed to move a model's score. After results exist, a
  question or its gold SQL changes only to fix a verified error, with the
  question id and the reason in `CHANGELOG.md`, and the affected questions
  are re-run.

## Setup

```bash
uv sync
make all   # ruff, mypy, pytest; CI runs the same, with DuckDB only
```

Real warehouses and model APIs need a `.env` (copy `.env.example`). Never
commit it.

## Adding a model

1. Add an entry to `models.yaml`:

   ```yaml
   - id: my-model                  # short, used in results and the report
     provider: openai              # anthropic | openai | google | openrouter | ollama
     model: my-model-2026-11-01    # the provider's model name
     version: my-model-2026-11-01  # pinned version recorded with every result
     max_tokens: 16000
     temperature: 0                # null if the API rejects the parameter
     input_usd_per_million: 1.00   # from the provider's pricing page, with the date
     output_usd_per_million: 4.00
     requests_per_minute: 50
   ```

   OpenRouter and Ollama models use the OpenAI-compatible client. A new
   API needs a client in `src/sqlbench/models/clients.py`, with tests that
   use a fake transport, not the network.

2. Check it with a small paid sample. The command prints a cost estimate
   and waits:

   ```bash
   uv run bench run --models my-model --per-schema 5 --run-id try-my-model
   ```

3. For a published result, run the full frozen set. Then export, and
   regenerate the report:

   ```bash
   uv run bench questions freeze --check
   uv run bench run --models all --run-id <new-run>
   uv run bench export --run-id <new-run>
   uv run bench rerun-gold
   uv run bench report --run <new-run>
   ```

Everything uses the same prompt (`prompts/v1.txt`) and is zero-shot. Don't
add per-model prompts or settings tuned to a model's score.

## Adding a question

1. Write `questions/<schema>/<schema>_NNN.yaml` with `status: draft`. Copy
   the format of an existing file; `docs/dataset_card.md` lists the fields.
   - State anything ambiguous in the question: time zone, string
     normalization, ties, whether empty groups appear, whether duplicates
     count.
   - Write gold SQL for both warehouses with bare table names (the session
     picks main or edge).
   - A `semantics` question needs a trap confirmed on both warehouses. Add
     the probe to `docs/semantics_probes.md` and name it in
     `divergence_note` as `(probe <name>)`.
   - Don't use features that are preview or beta on either warehouse.
2. Lint it, which is free:

   ```bash
   uv run bench questions lint
   ```

3. Check that both golds agree on main and edge. This runs on both
   warehouses and prints a cost estimate first:

   ```bash
   uv run bench questions check --schema <schema>
   ```

4. A maintainer reviews and verifies it in `bench questions verify`, which
   stamps `verified_by` and `verified_at`. Only verified questions are
   scored.
5. A new question changes the question-set hash. Re-freeze
   (`bench questions freeze`), tag the new inputs, and start a new run. Old
   runs stay as they are.

## Commits and pull requests

- Small commits with Conventional Commit messages, e.g.
  `fix(scorer): compare timestamps in UTC`.
- Tests that check real behavior and edge cases. No network in tests.
- `make all` must pass.
